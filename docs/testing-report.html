La estrategia de testing del proyecto GMS está organizada en tres capas independientes que cubren distintos niveles de la aplicación. Cada capa tiene su propia herramienta, su propio entorno de ejecución y su propio rol dentro del pipeline de CI/CD.

Capa Tipo Herramienta Entorno Tests Tiempo aprox.
Funciones puras Unitario Vitest 4 Sin dependencias externas 48 ~0.5s
Hooks React Integración Vitest + Testing Library Supabase mockeado 17 ~1s
Flujos de usuario E2E Playwright App + Supabase real En expansión ~5-10min

2. Pirámide de Testing

La distribución de tests sigue la pirámide clásica: muchos tests rápidos y baratos en la base, pocos tests lentos y costosos en la cima. Esto garantiza feedback rápido en desarrollo sin sacrificar cobertura real de los flujos críticos.

E2E (Playwright) — Flujos reales de usuario
Integración — Hooks con Supabase mockeado
Unitarios — Funciones puras, sin dependencias
Principio central: los tests de integración y unitarios no requieren ninguna credencial, servidor ni variable de entorno. Todo lo que depende de Supabase está reemplazado por mocks, lo que permite ejecutarlos en cualquier entorno —incluyendo CI— de forma completamente autónoma.

5. Tests de Integración

Los tests de integración prueban los hooks de React junto con su lógica interna, pero reemplazan las llamadas reales a Supabase con funciones simuladas (mocks). Esto permite verificar que los hooks responden correctamente a cada escenario sin necesidad de una base de datos real.

Estrategia de mock: se utiliza vi.mock('../lib/supabase', ...) para reemplazar el cliente de Supabase por completo. Las funciones del mock se declaran con vi.hoisted() para garantizar que estén disponibles en el momento en que Vitest hace el hoisting de vi.mock al inicio del archivo.

6. Tests E2E con Playwright

Los tests End-to-End simulan el comportamiento real de un usuario en el navegador, interactuando con la interfaz gráfica y la base de datos de Supabase en un ambiente real. Son los más lentos pero los que mayor confianza dan sobre el funcionamiento completo del sistema.

6.2 Patrón de autenticación

Los tests E2E utilizan storage state de Playwright para reutilizar sesiones autenticadas entre tests. Cada rol del sistema tiene su propio archivo de estado guardado, evitando el login en cada test individual.

9. Configuración de Vitest

// vitest.config.ts
import { defineConfig } from 'vitest/config'
import react from '@vitejs/plugin-react'

export default defineConfig({
  plugins: [react()],
  test: {
    environment: 'jsdom',        // simula el DOM del browser
    setupFiles: ['./src/tests/setup.ts'],
    globals: true,               // describe/it/expect sin imports
    include: ['src/**/*.test.ts', 'src/**/*.test.tsx'],
    exclude: ['e2e/**', 'node_modules/**'],
    coverage: {
      provider: 'v8',
      reporter: ['text', 'html'],
      include: ['src/lib/**', 'src/hooks/**'],
    },
  },
})
